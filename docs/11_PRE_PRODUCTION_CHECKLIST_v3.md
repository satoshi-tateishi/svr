# 11_PRE_PRODUCTION_CHECKLIST_v3.md

## 公演手配管理システム 本番前チェックリスト（人員・配車・PDF統合版）

* * *

# 目的

本チェックリストは、演劇制作特有の複雑なスケジュール管理において、以下の致命的リスクをゼロにすることを保証するために使用する。

-   **配車・人員の重複事故**: 現場にトラックが来ない、スタッフが足りない事態の防止。
-   **確定実績の改ざん**: 支払い・請求の根拠となるデータの不変性保証。
-   **テンプレート展開ミス**: 標準工程（1〜9）の漏れによる手配漏れ防止。
-   **情報漏洩**: 現場責任者（Chief）への原価・単価情報の秘匿。

* * *

# 1. 工程テンプレート & 乖離ロジック

### 1.1 テンプレート展開 (PhaseService)

-   [ ] `apply_production_template` 実行時に 9 つの Phase が正しい順序で生成される。
-   [ ] 既に Phase が存在する公演で再実行した際、二重作成が防止されている（冪等性）。
-   [ ] 生成された各スロットの `status` が初期値 `Draft` である。

### 1.2 希望 vs 確定 (Request/Assignment)

-   [ ] `VehicleOperation` の `requested_start` を入力しても `scheduled_start` が上書きされない。
-   [ ] 30分以上の時間乖離（Drift）がある場合、警告フラグが立つ。
-   [ ] 人員不足（希望 > 確定）の状態で Lock しようとした際、理由入力プロンプトが出る。

* * *

# 2. ダブルブッキング最終検証（物理・論理）

### 2.1 車輌（Vehicle）の重複

-   [ ] 同一車輌を同時刻の別工程にアサイン → **拒否**。
-   [ ] 外部車輌（`is_external=True`）の場合 → 重複判定から**除外**。
-   [ ] 自社車輌の「整備・車検」期間との重複 → **拒否**（整備をダミー案件として登録する場合）。

### 2.2 人員（Staff）の重複

-   [ ] 集合・解散バッファ（Occupied Time）を含めた時間帯での重複 → **拒否**。
-   [ ] 同一人物を「音響」と「搬入」など別ポジションで同枠にアサイン → **拒否**（または警告）。

### 2.3 排他制御 (Concurrency)

-   [ ] 2名のユーザーが同時に同じスタッフを別案件にアサイン → **片方が DB レベルで Lock 待機し、後続がエラーになる**。

* * *

# 3. 🔒 統合スナップショット & 不変性

### 3.1 財務スナップショット (FinancialSnapshot)

-   [ ] Lock 実行時に `applied_staff_cost` と `applied_vehicle_cost` が同時に保存される。
-   [ ] スナップショット JSON 内に、その時点の「確定運行時間」と「乖離理由」が含まれている。
-   [ ] `snapshot_hash` が SHA-256 で正しく生成され、手動改ざんを検知できる。

### 3.2 不変性の死守 (Immutable check)

-   [ ] ステータスが `Locked` のスロットに対し、API経由で `user_id` を変更 → **403 Forbidden / ValidationError**。
-   [ ] ステータスが `Locked` の配車工程に対し、運行時間を変更 → **拒否**。
-   [ ] 管理者であっても、Lock 解除なしに金額フィールドを直接更新できない。

* * *

# 4. 帳票出力 (PDF) 検証

-   [ ] PDF 上の金額が、スナップショット（`applied_*`）と完全に一致している。
-   [ ] PDF 生成時に、未確定（Draft/Assigned）のデータが含まれる場合に「暫定」の透かしが入る。
-   [ ] 外注先向けの「配車指示書」に、社内原価（単価）が**印字されていない**ことを目視確認。

* * *

# 5. 権限 & 秘匿性チェック

-   [ ] **Chief ロール**: 自分の担当公演のスケジュールは見れるが、単価・原価の API レスポンスが `null` または秘匿されている。
-   [ ] **Planner ロール**: 自公演の Lock はできるが、他人の公演の Lock 解除はできない。
-   [ ] **Admin ロール**: 緊急時の Lock 解除ができるが、その際 `UnlockReason` と `AuditLog` が強制記録される。

* * *

# 6. インフラ & 運用耐性 (Ubuntu 24.04 / MySQL 8)

-   [ ] **MySQL 8 JSON**: `FinancialSnapshot` の JSON 検索インデックスが効いている。
-   [ ] **バッファプール**: `innodb_buffer_pool_size` が 512MB 以上（推奨1GB）に設定されている。
-   [ ] **バックアップ**: `mysqldump` にスナップショットの JSON データが正しく含まれているか、リストアテスト済み。

* * *

# 7. リリース当日の手順 (Standard Operating Procedure)

1.  **DB Backup**: 現時点の全データを退避。
2.  **Deploy**: Docker image の更新と `migrate` 実行。
3.  **Template Test**: テスト用案件で 1〜9 のテンプレート展開を実行。
4.  **Lock Test**: テスト用案件を Lock し、PDF が正しく出るか確認。
5.  **Log Check**: `AuditLog` に上記操作がすべて記録されているか確認。

* * *

# 最低合格ライン (v3)

以下の 4 項目が **PASS** していなければ、リリースを延期すること。

1.  **ダブルブッキングの物理的阻止 (人員・車輌)**
2.  **Lock 後のデータ変更の完全遮断**
3.  **スナップショットと PDF 印字内容の完全一致**
4.  **権限による金額情報の秘匿（Chief 以下）**
