# PERMISSION_DESIGN_v2.md

## 公演手配管理システム 権限設計書（スナップショット確定対応版）

---

# 1. 設計思想

本システムは：

- システムロール（全体権限）
- 公演内ロール（公演単位権限）

の二層構造。

必ず：

View層で一次判定  
Service層で最終判定

を行う（二重防衛）。

さらに：

🔒 金額情報は機微情報として扱う。

---

# 2. ロール定義

## 2.1 システムロール

| Role | 説明 |
|------|------|
| Admin | 全権限 |
| Editor | 横断編集可 |
| General | 申請中心 |
| Viewer | 閲覧のみ |

---

## 2.2 公演内ロール

| Role | 説明 |
|------|------|
| Planner | 公演責任者 |
| Chief | 現場責任者 |
| Sub | 補助 |

# 6. 🔒 Locked解除ポリシー（強化）

原則：

- Lock解除機能はUIに出さない

Adminのみ：

- 緊急対応時に実行可能
- AuditLog必須
- API送信済の場合は警告表示

推奨運用：

> Lock解除ではなく、差額調整で対応

# 8. 状態依存制御

## 8.1 Locked時

- Staff変更禁止
- Position変更禁止
- 手当変更禁止
- 単価変更禁止
- occupied時間変更禁止

Service層で必ず検証。

---

# 9. Service層最終防衛

各Serviceの先頭で必ず：

1. system_role確認
2. performance所属確認
3. status確認
4. 金額閲覧可否確認

例：

get_confirmed_amount(slot_id, actor_user)

if actor_user.role not in [Admin, Editor]  
and performance_role != Planner:

    raise PermissionDenied

---

# 10. 横断権限

Editor：

- 全公演編集可
- Lock解除不可
- 単価登録可

Admin：

- 強制解除可
- 公演無効化可
- 監査ログ閲覧可

---

# 11. 監査ログ必須操作

- 単価登録
- 単価変更
- Lock実行
- Lock解除
- API再送
- 手当変更

削除不可。

---

# 12. 禁止事項（強化）

1. Chiefに単価表示しない
2. Lock後金額編集しない
3. Lock解除を常用しない
4. JavaScriptのみで制御しない
5. Modelで権限判定しない

---

# 13. 将来拡張余地

- 金額閲覧を二段階承認制にする
- 単価登録を承認制にする
- 公演単位で単価閲覧権限制御

現設計は拡張可能。
