# REQUIREMENTS_v3.md

## 音響会社用公演手配管理システム（AI実装 + プロンプトテンプレ同梱版）

------------------------------------------------------------------------

# 1. プロジェクト目的

## 最優先

管理負荷を減らす

## 次点

-   手配ミスをなくす
-   情報共有を楽にする

## 優先度低

-   経営データ可視化

------------------------------------------------------------------------

# 2. 設計原則（絶対遵守）

1.  公演担当者主導型とする。
2.  Request と Assignment は物理的に別モデルとする。
3.  占有時間はバッファ込みで管理する。
4.  物理削除は禁止（is_active による論理削除）。
5.  既存モデルの破壊的変更は禁止。拡張は新規モデル追加で行う。
6.  外部API連携は初期リリースでは実装しない。
7.  system_role と performance_role は完全に独立させる。

------------------------------------------------------------------------

# 3. ロール設計

## 3.1 システムロール

User.system_role: - Admin - Editor - General - Viewer

## 3.2 公演内ロール

PerformanceMember: - performance (FK) - user (FK) - role - Planner -
Chief - Sub

同一ユーザーが複数公演で異なるroleを持つことを許容する。

------------------------------------------------------------------------

# 4. エンティティ構造

Performance 
└── PerformancePhase 
    └── PhaseSlot 
        ├── PhaseSlotRequest(1:1) 
        └── PhaseSlotAssignment (1:1) 
            ├── StaffAssignment (M2M) 
            └── VehicleAssignment (FK)

------------------------------------------------------------------------

# 5. 占有時間ロジック（固定仕様）

occupied_start = start_datetime - travel_buffer_before_minutes\
occupied_end = end_datetime + travel_buffer_after_minutes

ダブルブッキング判定は occupied時間帯の重複で行う。

------------------------------------------------------------------------

# 6. ステータス管理

Draft: Planner / Chief 編集可能

Requested: Planner / Chief 編集不可 Editor以上 Assignment作成可能

Assigned: Editor以上 編集可能

Locked: Adminのみ解除可能 全ロール編集不可

------------------------------------------------------------------------

# 7. ダッシュボード

## 個人

-   自分のスケジュール
-   自分が担当する公演のスケジュール
-   他公演のスケジュール（閲覧のみ）

## 管理者

-   今日の工程
-   明日の工程
-   指定日の工程 
-   車両稼働状況
-   人員稼働状況

------------------------------------------------------------------------

# 8. MVP範囲

Assignment登録 - ダブルブッキング検出 - PDF出力

# 10. AI実装用プロンプトテンプレ

## Djangoモデル生成用プロンプト

あなたはシニアDjangoエンジニアです。
REQUIREMENTS_v3.mdに厳密に従い、models.pyを作成してください。

制約: - RequestとAssignmentは必ず別モデルにすること - 物理削除は禁止 -
占有時間ロジックはservice層で実装する -
system_roleとperformance_roleを混同しない - 既存モデルを破壊しない

出力形式: - models.py のみ出力 - 説明文は不要

------------------------------------------------------------------------

## ダブルブッキング判定ロジック生成用プロンプト

occupied_start / occupied_end を使用して
重複判定関数を実装してください。

制約: - QuerySetベースで実装 - パフォーマンスを考慮 -
テストコードも含める

------------------------------------------------------------------------

## 権限制御実装用プロンプト

system_role と performance_role を両方確認する
permission関数を実装してください。

制約: - ロジックを関数に分離 - ifのネストを深くしすぎない -
再利用可能な設計にする

------------------------------------------------------------------------

## 破壊的変更防止プロンプト

設計思想が不明確な場合、
既存モデルを変更せず新規モデルを追加して拡張してください。

既存フィールド削除は禁止です。
